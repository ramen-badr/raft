# Raft — этап 1: каркас

Реализация консенсуса Raft по [статье Ongaro и Ousterhout](https://raft.github.io/raft.pdf) на Go.
Текущее состояние — **этап 1**: P2P-связь между отдельными процессами, выборы лидера с термами,
heartbeat как пустой `AppendEntries`, клиентский эндпоинт статуса.

## Запуск

```bash
./scripts/cluster.sh start 5    # поднять 5 узлов
./scripts/cluster.sh status     # состояние всех узлов
./scripts/cluster.sh stop       # остановить
./scripts/cluster.sh rm         # остановить и очистить логи
```

Скрипт собирает бинарник, поднимает узлы отдельными **процессами** (требование курса: горутины
внутри одного процесса не считаются), пишет логи в `.cluster/nodeN.log` и сразу печатает статус.

Вручную один узел:

```bash
go run ./cmd/node -id 0 -http 127.0.0.1:8001 \
  -peers 0=127.0.0.1:8001,1=127.0.0.1:8002,2=127.0.0.1:8003
```

## Клиентский API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/status` | роль, терм, текущий лидер, живые пиры |
| `POST` | `/raft/request-vote` | RPC `RequestVote` между узлами |
| `POST` | `/raft/append-entries` | RPC `AppendEntries` между узлами (heartbeat) |

```console
$ curl -s localhost:8001/status | jq
{
  "id": 1, "state": "Leader", "term": 2, "leaderId": 1,
  "peers": [0, 2], "alivePeers": [0, 2]
}
```

## Структура

```
raft/raft.go        ядро: состояние узла, переходы ролей, обработчики RPC, таймеры
raft/http.go        транспорт RPC поверх HTTP+JSON и монтирование маршрутов
api/api.go          клиентский REST-контроллер
cmd/node/main.go    точка входа узла
scripts/cluster.sh  запуск кластера из N процессов
```

Разделение намеренное: `Transport` — интерфейс, поэтому ядро не знает про HTTP. `Node` — система переходов «сообщение → новое состояние →
исходящие сообщения», как на лекции.

## Тайминги

- Heartbeat — каждые **0.1 с**.
- Leader election timeout — случайная величина из **[0.5 с, 1 с]**, **перевыбирается заново на каждый
  цикл ожидания**. Фиксированный таймаут приводит к тому, что узлы синхронно уходят в кандидата
  и терм растет бесконечно без стабильного лидера.

## Что реализовано из Figure 2

- Состояние: `currentTerm`, `votedFor` (в памяти; диск для этапа 1 не нужен).
- Роли follower / candidate / leader, переходы по таймауту и по терму.
- `RequestVote` (`term`, `candidateId`): отказ при устаревшем терме, правило «голос один за терм».
- `AppendEntries` (`term`, `leaderId`) без записей — heartbeat: сброс таймера выборов, принятие лидера,
  отказ при устаревшем терме.
- Только один лидер на терм: каждый узел голосует не более одного раза за терм.

## Ручной сценарий для показа

1. `./scripts/cluster.sh start 3` → в течение ~1 с один узел станет `Leader`, остальные — `Follower` с тем же термом.
2. `curl localhost:8001/status` → видно `leaderId` и живые пиры.
3. Убить процесс лидера → терм увеличивается, новый лидер выбирается за 0.5–1 с.
4. Запустить убитый узел с теми же флагами → он возвращается фолловером и признает нового лидера.
